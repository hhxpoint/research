# hhxpoint/research 发布前独立审计报告

- 审计对象：`<repo>`
- 审计日期：2026-11-23
- 审计方式：只读审计；仅在 `%TEMP%` 下创建临时 DSH home / 仓库副本做验证；未联网、未推送、未修改仓库文件
- 审计快照：`HEAD = de0f124`（`docs: 修正 --from-installed 说明`），工作树干净；审计期间仓库从 `abd99be` 演进到 `de0f124`，本报告以 `de0f124` 为准
- 目标：GitHub `hhxpoint/research`；DSH 44.7.0；Python 本机 3.10.11 / PyYAML 6.0.3

## 0. 结论

**工程骨架可用，但当前版本不建议直接公开发布（NO-GO），需先修 7 项必须修问题。**

已验证通过的部分：

- `selftest`：15 个技能、ARS 归档全部通过；
- `build_lock.py --check`：锁文件、归档、仓库明文技能一致；
- 19 个 unittest 全部通过（约 138 秒）；
- 临时 DSH home 全量安装 15 个技能、`verify --require-all`、`list --json`、`uninstall --keep` 全部符合预期；
- tar 的绝对路径、`..`、符号链接、硬链接防护有效；
- 文档相对链接无缺失，未发现真实密钥或本机绝对路径进入被跟踪文件；
- `.gitignore` 覆盖 `__pycache__` / `*.pyc`；发布包体积约 4.7 MB，无超大二进制。

必须修的核心原因：

1. ARIS 3 个技能的实际来源是 **`unpinned (jsDelivr @main)`**，但 README/THIRD-PARTY/锁文件/SECURITY 宣称固定 commit `4ba94ae2...`，可复现性声明不成立；
2. `uninstall --force` 可借 `..`、绝对路径删除 `$DSH_HOME/skills` 之外的任意目录（实测可删掉整个临时 DSH home）；
3. 安装到 `$DSH_HOME/skills` 的副本不含 MIT/CC BY-NC 许可证文本与版权声明；`venue-templates` 还混入了 Elsevier LPPL 文件，但顶层许可证表只写 K-Dense MIT；
4. `--no-backup` 下安装中途失败会丢掉旧技能，而 README/安装文档承诺“失败回滚、不会半安装”；
5. `verify` 的哈希不符实际返回 1，文档却把“哈希不符”归到退出码 3；
6. `build_lock --from-installed` 会把 `__pycache__`/`.pyc` 等任意已安装文件打进 tar 和锁文件，且先覆盖 tar 再校验，失败会留下 tar/锁不一致；
7. 上述问题在现有测试中均无覆盖，CI 全绿不能证明这些路径安全。

**位置：** `tools/dsh_skills.py:497-519`


**实测（临时目录，仅测试数据）：**

4. 增加测试：`..`、绝对路径、`../`、Windows 盘符、UNC 均拒绝且不删除任何文件。

### M3【严重】安装副本缺少 MIT/CC BY-NC 许可证文本与版权声明

**证据：**

- `skills/` 下 0 个 `LICENSE` / `NOTICE` / `COPYING` 文件；`vendor/ars-...tar.gz` 980 个成员中 0 个许可证文件；
- `vendor/licenses/` 只有 5 个许可证原文，但 `cmd_install`/`materialize` 只复制 `staging/<name>` 到 `$DSH_HOME/skills/<name>`（`dsh_skills.py:254-271`、`:400-414`），不会把 `vendor/licenses/` 或 `THIRD-PARTY.md` 带到安装目录；
- `skills/*/DSH-PORT.md:5` 只写 `license: MIT`，ARS 的 DSH-PORT 只写 `license: CC BY-NC 4.0 仅限非商业学术用途`，没有 MIT 完整声明，也没有 ARS 作者 `Cheng-I Wu` 的署名；
- `README.md:167` 宣称“MIT 保留版权声明”、`THIRD-PARTY.md:32` 宣称“本仓库已保留”，但这些只在仓库层，不在实际安装产物里；`vendor/ARS-NOTICE.md`（当前已跟踪）也只位于仓库 `vendor/`，不会被安装。
- CC BY-NC 4.0 要求分享时提供许可证副本、署名、修改说明；MIT 要求在所有副本中包含版权声明和许可声明。

**影响：** 用户只拿到 `~/.dsh/skills/<name>/` 时，既没有 MIT 许可文本，也没有 CC BY-NC 许可文本/作者署名；若用户再分发安装后的技能目录，存在许可证合规风险。这是发布前的法律阻断项。

**修复建议（二选一或组合）：**

1. 在每个技能目录放 `LICENSE`/`NOTICE`（MIT 用对应版权声明，ARS 用 CC BY-NC 4.0 摘要 + 作者/来源/修改说明），并纳入锁文件；
2. 安装器额外安装 `$DSH_HOME/skills/.licenses/`（无 `SKILL.md`，DSH 不会当技能加载）和 `THIRD-PARTY.md`，并在每个 `DSH-PORT.md` 写相对链接；注意 `verify`/锁文件要把这些文件纳入或明确忽略；
3. 至少给 ARS `DSH-PORT.md` 补作者 `Cheng-I Wu` 和许可证 URL；给 MIT 技能补版权行。

### M7【中】`build_lock --from-installed` 非 hermetic，且会先覆盖 tar 再校验

**位置：** `tools/build_lock.py:220-249`、`:352-358`、`:414`

**实测 1（污染）：** 在临时 DSH home 的 `academic-paper/__pycache__/` 放一个 `.pyc`，执行 `--from-installed` 后：

- tar 内出现 `academic-paper/__pycache__/pollute.cpython-310.pyc`；
- 锁文件也记录该文件；
- 若该 pyc 是用户运行技能脚本产生的，可能包含本机绝对路径，并被发布到 GitHub。

**实测 2（部分写入）：** 在仓库副本中删除 `skills/research-stack/SKILL.md`，再执行 `--from-installed`：

- 程序先重写 `vendor/ars-...tar.gz`，随后因缺少普通技能而退出 1；
- 结果：tar 哈希已改变，锁文件仍是旧内容，仓库处于不一致状态；
- 只有再次手工修复/重建才能恢复。

**原因：**

- `build_ars_tarball` 用 `d.rglob("*") if p.is_file()` 收集所有文件，没有排除 `__pycache__`、`*.pyc`、`.DS_Store`、`Thumbs.db` 等；
- `main()` 在 `:354` 先写 tar，之后 `:357` `gather_skill_dirs`、`:358` `build_lock`、`:414` `write_lock` 才可能失败；没有“先构建内存结果、校验后再写”的顺序。

**修复建议：**

1. `build_ars_tarball` / `skill_files` 统一排除 `__pycache__`、`*.pyc`、`*.pyo`、`.DS_Store`、`Thumbs.db`、`.git`、编辑器临时文件；
2. 先在内存中构建 tar 字节和锁对象，校验所有普通技能/ARS 后，再原子写 tar 和锁；或先写临时 tar，成功后再 `replace`；
3. `--from-installed` 明确要求使用“干净临时 DSH home”，不要用日常 `~/.dsh`；文档 `docs/maintenance.md:29-30` 当前建议在开发机安装后重建，容易污染；
4. 增加测试：`--from-installed` 两次干净重建字节一致；人为放入 `__pycache__` 后必须被忽略或报错；缺少普通技能时 tar/锁均不变。

## 2. 建议修（不阻断发布，但应尽快处理）

### S1【中】tar 特殊文件未拒绝，`filter="data"` 仅靠 TypeError 回退

- `tools/dsh_skills.py:229-244` 只拒绝绝对路径、`..`、符号链接、硬链接，没有拒绝 FIFO/设备文件；本机 Python 3.10.11 的 `TarFile.extractall` 没有 `filter` 参数，走 `except TypeError` 的无过滤分支。
- 实测：带 FIFO 成员的 tar 被 `extract_archive` 接受且不报错（Windows 上落为普通文件；Linux 上可能创建 FIFO）。
- `tools/build_lock.py:153-166` 的 `safe_extractall` 完全没有 `filter`，也不拒绝特殊文件。
- 建议：拒绝所有既非普通文件也非目录的成员；用 `hasattr(tarfile, "data_filter")` / 检查签名判断是否支持 filter，不要用宽泛 `except TypeError`；`safe_extractall` 复用同一套检查；补 FIFO/字符设备/Windows 保留名/ADS 的测试。
- 由于归档 sha256 被锁文件固定，实际利用需要同时改锁文件，风险等级降为“中”；但这是安全边界的一部分，应补上。

### S2【中】DSH 前端校验没有拒绝 camelCase 调用键

- `tools/dsh_skills.py:191-210` 的 `validate_skill_dir` 只检查 `name`、`description`、body；不检查 `disableModelInvocation`/`modelInvocable`/`userInvocable`。
- 文档 `docs/dsh-skill-spec.md:53` 明确说 DSH 对驼峰键会静默丢弃技能；如果将来新增技能误带该键，`selftest`/`verify` 会通过，但 DSH 里看不到技能。
- 建议：在 `validate_skill_dir` 中拒绝驼峰调用键（或给出 warning），并增加一个负向测试。

### S3【中】`--only` 重复名/OSError 会抛 traceback，退出码语义混乱
