# 实验观察：先把过程看全，再下结论

> 提炼自 karpathy/autoresearch（100.5k★，固定 5 分钟预算 + 单指标 val_bpb + git 记忆 + 只改一个文件）、
> uditgoenka/autoresearch（6.9k★，Modify→Verify→Keep/Discard、TSV 记账、fork-and-flush）、
> ARIS `analyze-results`（19.7k★，Observation→Interpretation→Implication→Next step）与 ML 实验工程实践。

## 0. 核心原则

- **观察 ≠ 结论**：日志、曲线、错误样例是"发生了什么"；机制解释是下一步。
- **完整先于漂亮**：失败 run、异常、偏差和成功 run 一样要记录；删掉不利 run 等于篡改证据。
- **可复现先于可解释**：先保证 run id / 配置 / 数据 / 代码 / 种子可追溯，再谈为什么。
- **单指标 + 固定预算**（Karpathy 经验）：迭代时固定训练预算与唯一判定指标，减少"看起来变好"的自由度。
- **git 即记忆**（uditgoenka 经验）：每次只改一处，先 commit 再验证；好则 keep，坏则 revert，结果写 TSV。

## 1. 每次 run 必须记录（缺一项就不算可分析）

| 字段 | 说明 |
|---|---|
| run id | 唯一、可排序（日期-序号或 uuid） |
| git commit | 代码版本；工作区脏要标记 dirty |
| 完整配置 | 所有超参、模型/数据配置、环境变量（脱敏） |
| 数据版本 | 数据集名/版本/校验和/划分文件 |
| seed | 每个 run 的随机种子（含数据打乱、初始化、dropout） |
| 硬件/环境 | GPU 型号/数量、CUDA/PyTorch 版本、容器镜像 |
| 时长/成本 | 起止时间、GPU-hours、估算费用 |
| 逐 step 指标 | train/val loss、主指标、学习率、梯度范数、吞吐 |
| 评测协议 | 评测脚本版本、解码参数、后处理、评测集 |
| 产物路径 | checkpoint、预测文件、日志、曲线、样本输出 |
| 状态 | running / done / crashed / killed / invalid（及原因） |

建议用追加式 `runs.jsonl` 或 tracker 表；日志只追加不修改。原始预测/结果文件保留，不要只留汇总。

## 2. Sanity checks（烧大算力之前）

- 单 batch 过拟合：模型能否在 1–2 个 batch 上把 loss 降到接近 0？不能则代码/标签/损失有问题。
- 指标自测：用已知答案的小样例验证 metric（全对=100，全错=0，边界值正确）。
- 打乱标签/随机输入：应退化到随机水平；如果仍很高 → 泄漏。
- baseline 复现：用官方/论文设置跑通 baseline，差距大先查协议。
- 泄漏探针：训练/验证/测试重叠检查；预训练数据与评测集重叠；按 subject/时间分组是否泄漏。
- 确定性检查：同 seed 重跑是否一致（GPU 非确定性要记录）。
- 数据分布抽查：类别比例、长度分布、缺失/异常值、label 噪声样本。

## 3. 训练/评测中的观察

- 看曲线形状：早停点、过拟合拐点、loss 尖峰、平台、断崖；异常先复现再解释。
- 监控：NaN/Inf、梯度爆炸/消失、吞吐异常、显存溢出、eval 抖动、数据加载瓶颈。
- 对比必须同协议：同一评测脚本、同一解码/后处理、同一数据划分；换协议要在表中注明。
- dev/val 用于选择与决策；test 只在最后用一次，不许反复调 test。
- 早停/模型选择规则提前定；不要用 test 选 checkpoint。
- 每轮迭代只改一个变量；改多处无法归因。记录"预期 vs 实际 vs 惊讶点"。
- 训练不稳定时先降复杂度/学习率/精度，再谈方法优劣。

## 4. 异常 triage 流程

1. **复现**：同配置同 seed 再跑一次；不稳定则记录方差。
2. **定位层级**：数据（分布/标签/泄漏）→ 代码（bug/实现差异）→ 指标（计算/聚合错误）→ 训练（优化/超参）→ 评测（协议/后处理）。
3. **对照**：与 baseline 同条件对比；做最小改动定位变量。
4. **分类**：bug / 方差 / 真效应 / 数据问题 / 环境差异。
5. **记录**：结论、证据、下一步探针；不要只留一句"结果不好"。

## 5. 观察笔记模板（可直接写进 RESULTS.md 的 Observations）

```markdown
### Run R012 · <一句话目的>
- 配置/命令：<commit> <config> <seed>
- 预期：<开跑前的预测>
- 实际：<关键数字/曲线/异常>
- 惊讶点：<与预期不符之处>
- 失败/异常：<NaN/崩溃/被 kill/数据问题>
- 初步解释（假设，不是结论）：<...>
- 下一步探针：<最小实验验证该解释>
```

## 6. 可复现性最低标准

- 一条命令能从原始数据复现主表（脚本 + 配置 + 数据校验和 + 环境锁）。
- 记录所有随机源；固定 seed 后仍要报告多次运行的方差。
- checkpoint/预测文件可复算主指标；不允许"只保留最终数字"。
- 环境：`pip freeze`/lockfile/容器镜像；GPU 型号与驱动。
- 数据：版本、划分文件、预处理脚本、许可与访问条件。

## 7. 失败分类（用于失败分析章节）

| 类型 | 例子 | 处理 |
|---|---|---|
| bug | 标签错位、mask 错、评测脚本 bug | 修复并重跑；旧结果标记 invalid |
| 泄漏 | train/test 重叠、预训练污染 | 修划分/换评测；结论作废 |
| 方差 | 小数据/单 seed 抖动 | 多 seed、CI、配对检验 |
| 真效应 | 方法在某 slice 确实差 | 写入失败分析/limitations |
| 实现差异 | 与 baseline 实现/库版本不同 | 统一实现或注明 |
| 环境 | OOM、硬件差异、驱动 | 记录并重跑 |

## 8. 反模式

- 只看最终指标，不看训练曲线/异常
- 删除失败 run、只报最好的 seed
- 用 test 调参/选模型；不同实验用不同评测协议
- 改了配置没记录，事后无法解释差异
- 只留 notebook 输出，不留脚本/配置/数据版本
- 把方差当效应；把偶然尖峰当机制
- 在日志里只写"loss 下降"（没有数字、没有条件）

## 9. 与 auto-research 的对应

- `experiments` 阶段：先确认 run 记录完整（上表），再写 `RESULTS.md` 的 `## Observations`；
  失败与偏差写 `## Deviations`；统计写 `## Statistical checks`。
- 任何"我们观察到 X"的句子都要能指到 run id/日志/图；指不到就先补记录，不要写进论文。
